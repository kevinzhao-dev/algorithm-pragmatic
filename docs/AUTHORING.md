# Exercise format

This document defines the format of every exercise. Follow it to add one of your own. Examples:

- An implementation exercise: [`problems/6.006/0114-doubly-linked-list`](../problems/6.006/0114-doubly-linked-list/README.md). Its reference solution is at the same path under `solutions/`.
- A written exercise: [`problems/6.006/0111-asymptotic-ordering`](../problems/6.006/0111-asymptotic-ordering/README.md)

## Layout

```
problems/<course>/<UUNN-slug>/
    README.md        the exercise
    solution.hpp     the skeleton, where the learner writes code (more *.cpp files are allowed)
    tests/*.cpp      tests
    support/         (optional) fixed helpers, used by both builds
    practice.cmake   (optional) extra compile flags; may use ${target}
solutions/<course>/<UUNN-slug>/
    solution.hpp     the reference solution, with the same interface as the skeleton (more *.cpp files are allowed)
problems/<course>/_shared/   (optional) fixed helper headers shared within a course
```

Tests always `#include "solution.hpp"`. The build switches between the skeleton and the reference solution through the include path, so `tests/` must not contain a `solution.hpp`.

## Numbering: `UUNN`

**`UU` is the unit.** 6.006 and 6.046J follow the problem set numbers. 6.172 follows the course schedule:

| UU | Contents | UU | Contents |
| --- | --- | --- | --- |
| 01 | HW1 | 08 | HW6 |
| 02 | HW2 | 09 | HW7 |
| 03 | Project 1 | 10 | Project 3 |
| 04 | HW3 | 11 | HW8 |
| 05 | HW4 | 12 | HW9 |
| 06 | HW5 | 13 | HW10 |
| 07 | Project 2 | 14 | Project 4 |

**`NN` is the exercise:**
- `01`–`09`: **core implementations**. You write the data structures and algorithms taught in the unit's lectures and recitations yourself. They come before the assignment problems.
- `11`–`19`: **assignment problems**. The last digit is the problem number, so Problem 1-4 of PS1 is `0114`.
- `21`–`29`: extensions, or parts split off from the unit's other exercises.

## README

The README starts with front matter, one `key: value` per line:

| Field | Required | Description |
| --- | --- | --- |
| `title` | yes | A short title |
| `unit` | yes | For example `01 · Sequences (PS1)`. It must be identical for every exercise in a unit, because ROADMAP groups by it |
| `source` | yes | For example `6.006 PS1 Problem 1-4`; for a core implementation, `6.006 Recitation 2` |
| `pdf` | yes | The original problem or lecture-notes PDF, relative to the repo root |
| `answer` | no | The official solution PDF |
| `read` | no | PDFs to read before starting, comma-separated |
| `kind` | yes | `code`, `perf`, `project` or `paper` |
| `minutes` | yes | Estimated minutes. Be honest |
| `sanitizer` | no | Set it to `tsan` to run the functional tests under ThreadSanitizer |
| `timeout` | no | The time limit for one run, in seconds. The default is 60 |

The body comes in this order:

1. **Title:** `# UUNN · Name`.
2. **Link line:** links to the `pdf` and `read` files on OCW. It's generated by `python3 -I tools/readme_links.py <path to README.md>`, so don't write it by hand.
3. **Why this comes up in practice:** a quote of one or two concrete sentences on where real systems run into this. Leave it out rather than make something up.
4. **`## Original problem`:** required for assignment problems. Restate the original problem completely, in your own words: every given value, definition and part. Nobody should need the PDF. Don't include the official answers.
5. **`## Your task`:** what the exercise asks you to build and how it differs from the original. Follow it with "Write your code in `solution.hpp`. Each stage lists the declarations it adds, copied from that file."
6. **Stages:** map the assignment's parts onto stages. Requirements arrive one stage at a time, and earlier tests stay in force.
   - Each stage starts with a ```cpp block of the declarations it adds. Copy them from `solution.hpp`, replacing `{ PRACTICE_TODO(); }` bodies with `;`.
   - The last stage can be a real-world extension that uses what the exercise built to make a small but realistic component.
7. **`## Interview follow-ups`:** two or three questions to answer out loud afterwards. Focus them on trade-offs, failure scenarios and the reasons behind decisions.
8. **Official solution:** a link at the end, also generated by `tools/readme_links.py`.

Write in English. Identifiers and code comments are in English too, and comments only say what isn't obvious.

## Kinds

- **`code`:** a regular implementation, graded automatically. **Prefer turning problems into this kind.** Design problems that ask you to "describe an algorithm" should all become code exercises with an interface and tests.
- **`perf`:** performance engineering. Measure against a baseline in the same executable, as a ratio (for example, at least 3× faster). Don't hard-code absolute times.
- **`project`:** a large exercise that spans several files and stages.
- **`paper`:** only for pure proofs or pure analysis that really can't become code. The answer goes in `answer.md` in the exercise folder. When you're done, compare it with the official solution and run `./practice done <number>`.

## Skeleton

- `solution.hpp` contains only the interface and `PRACTICE_TODO();`. It must compile as is, and it contains no hints.
- Don't call `PRACTICE_TODO()` inside a `noexcept` function, or the program terminates immediately.
- Destructors must not throw. Leave them empty and let the tests catch what's missing.

## Tests

Use `TEST`, `PERF`, `CHECK*`, `REQUIRE*` and `INFO` from `harness/practice.hpp`, plus `Rng`, `Counted` and `Tracked`.

Every exercise needs these:

- **One test per edge case,** named after the behavior, for example `"deleting the only node empties both ends"`.
- **Randomized differential tests wherever a comparison is possible.** Use a brute-force solution or the standard library as the model. `Rng` uses a fixed seed by default, so failures reproduce. Use `INFO` to attach the step or the input.
- **A `PERF` test for every complexity requirement,** or count comparisons with `Counted`, which is more deterministic and therefore preferred.
  - `PERF` inputs must be large enough that a brute-force solution exceeds the budget at least 10 times over.
  - The budget must be at least 3× the reference solution's measured time.
- **Leak checks with `Tracked`** for every type that owns resources. Apple Silicon has no LeakSanitizer.
- **Only the public interface.** Tests may use only what the README documents, never implementation details.
- **No flakiness.** Don't depend on `unordered_map` iteration order, thread scheduling or the machine's absolute speed.

Functional tests must pass under ASan/UBSan. Keep each exercise's total run time under 10 seconds where possible.

## Acceptance

Every exercise must pass:

```bash
./practice audit --only '6\.006/0114'
```

The audit checks two things:

- The skeleton compiles and reports that it isn't implemented yet.
- The reference solution passes every test under ASan/UBSan and in Release.

The reference solution must be a real implementation, not one written around the test data.

For key exercises, also confirm that the tests catch mistakes. Write a deliberately brute-force or buggy version, and check that a `PERF` or functional test fails.

## Originality

MIT's lecture notes and assignments are in `materials/`, for reading only. **Don't copy their text, code or test data** into exercises, skeletons, tests or reference solutions.

- **Problem statements:** write them in your own words.
  - The `## Original problem` section restates the original in full, but in your own words.
  - Facts such as given values, definitions, formulas, problem numbers, algorithm names and complexities may be stated exactly.
  - In the stages, swap the original's stories and characters for engineering scenarios.
- **Interfaces, tests and reference solutions:** design and write them yourself.
- **MIT's code, pseudocode and figures:** never reproduce them; describe them instead.
- **Self-contained:** don't send the reader to the PDF for anything they need to do the exercise. Put it in the README.

## Environment

macOS arm64, Apple clang 21, libc++, C++20, standard library only.

- **Missing tools:** there is no `perf`, `valgrind`, `cachegrind`, `gdb` or `awsrun`. You can use `lldb`, `leaks`, `sample`, `xctrace` and clang's `-Rpass`.
- **Cilk:** not available. Use `fork2` and `parallel_for` from [`harness/forkjoin.hpp`](../harness/forkjoin.hpp).
- **x86 assembly and AVX:** rewrite that material as portable C++ checked with compiler reports, or use ARM NEON.
- **Cache behavior:** use a deterministic cache simulator, or measure against a baseline as a ratio.
